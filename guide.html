Bubble sort Try it

Swap neighbors that are out of order; each pass bubbles the largest item to the end.

Use it to learn. Stop early when a pass makes no swaps.

Insertion sort Try it

Grow a sorted prefix; slide each new item left until it fits.

Use it for tiny or nearly sorted arrays. Real sorts switch to it below ~16 items.

Selection sort Try it

Find the minimum of the unsorted part and swap it into place.

Use it when writes are expensive: at most n−1 swaps.

Merge sort Try it

Split in half, sort each half, merge the two sorted halves.

Use it when you need stability or guaranteed n log n, for linked lists, or for external sorting of huge files.

The merge step needs O(n) extra memory for arrays.

Quicksort Try it

Pick a pivot, partition smaller items left and larger right, recurse on both sides.

Use it as the fast in-memory default. Quickselect finds the k-th smallest in O(n) average.

Always picking the first or last element as pivot degrades to O(n²) on sorted input; pick randomly or median-of-three.

Heapsort

Build a max-heap, then repeatedly move the max to the end.

Use it for guaranteed O(n log n) with O(1) extra memory.

Counting / radix sort

Don't compare: count occurrences of each key, or sort digit by digit.

Use it for integers or short strings in a small range: beats n log n.

Searching

Binary search Try it

O(log n)O(1) space

On sorted data, compare with the middle and throw away the half that can't contain the answer.

Off-by-one errors: decide whether hi is inclusive and keep it consistent. Use lo + (hi - lo) / 2 in languages with overflow.

Binary search on the answer

O(log range · check)

If "can we do it with x?" is false then true as x grows, binary-search the smallest x that works.

Signals: "minimum maximum", "smallest capacity", "fewest days".

Two pointers Try it

O(n)

Move two indices toward each other (or in the same direction) and use sortedness to skip work.

Use it for pair sums in sorted arrays, removing duplicates in place, merging, palindromes.

Hash lookup

O(1) averageO(n) memory

Trade memory for time: store what you've seen so each lookup is instant.

Use it for "have I seen this?", counting, two-sum on unsorted data.

Graphs

Many problems are graphs in disguise: grids, dependencies, states of a puzzle, friendships, routes. First decide: directed or not, weighted or not, and whether there are negative weights or cycles.

Breadth-first search Try it

O(V + E)

Explore in rings using a queue; the first time you reach a node is via the fewest edges.

Use it for shortest paths in unweighted graphs and grids, levels, spreading processes.

Mark nodes as seen when you enqueue them, not when you dequeue, or you add duplicates.

Depth-first search Try it

O(V + E)

Go as deep as possible, then backtrack (recursion or an explicit stack).

Use it for connectivity, counting components, cycle detection, topological order, flood fill.

Deep recursion can overflow the stack on big inputs; switch to an explicit stack.

Dijkstra Try it

O((V + E) log V)

Always finalize the closest unfinished node, using a priority queue.

Use it for shortest paths with non-negative weights.

Wrong with negative edges. Skip stale queue entries whose distance is outdated.

A* search Try it

≤ Dijkstra in practice

Dijkstra ordered by g + h, where h estimates the remaining distance.

Use it for one start, one goal, with a good heuristic (maps, games).

h must never overestimate, or the path may not be shortest.

Bellman–Ford

O(V · E)

Relax every edge V−1 times; a further improvement means a negative cycle.

Use it with negative weights, or to detect negative cycles (arbitrage).

Floyd–Warshall

O(V³)O(V²) memory

For each middle node k, try improving every pair i→j through k.

Use it for all-pairs distances on small graphs (V ≤ ~400).

0-1 BFS

O(V + E)

Weights are only 0 or 1: push 0-edges to the front of a deque, 1-edges to the back.

Topological sort Try it

O(V + E)

Kahn: repeatedly output a node with no incoming edges. Or reverse DFS finish order.

Use it for build orders, course prerequisites, task scheduling.

If not every node comes out, the graph has a cycle.

Prim / Kruskal Try it

O(E log V)

Minimum spanning tree. Prim grows one tree with a heap; Kruskal adds the lightest edges that don't make a cycle, using union-find.

Use it to connect everything as cheaply as possible (networks, clustering).

Strongly connected components

O(V + E)

Tarjan (one DFS with low-links) or Kosaraju (DFS, reverse graph, DFS again).

Use it for groups that can all reach each other, 2-SAT, simplifying a graph to a DAG.

Bipartite check

O(V + E)

Two-color with BFS/DFS; a conflict means an odd cycle.

Use it for "split into two groups with no conflicts inside a group".

Trees & heaps

Traversals

Pre-order (node, left, right) copies/serializes. In-order (left, node, right) gives sorted order of a BST. Post-order (left, right, node) computes sizes/heights and deletes. Level order is BFS.

Binary search tree

O(h) per op

Left subtree < node < right subtree. Balanced variants (red-black, AVL) keep h = O(log n).

Inserting sorted data into an unbalanced BST makes a linked list: O(n) per op.

Heap / priority queue

O(log n) push/pop

A complete binary tree stored in an array; parent of i is ⌊(i−1)/2⌋. Building one from n items is O(n).

Use it for top-k, merge k sorted lists, running median (two heaps), schedulers.

Lowest common ancestor

O(log n) per query

Binary lifting: precompute 2k-th ancestors, then lift both nodes.

Trie

O(L)

A tree of characters; each path from the root spells a prefix.

Use it for autocomplete, word games, IP routing, many-pattern search.

Fenwick & segment trees

O(log n) query/update

Prefix sums (Fenwick) or any associative range query like min/max/sum (segment tree) that stays fast while values change.

Greedy

Make the locally best choice and never look back. Fast and simple, but only correct when you can argue that a best choice now never blocks a better solution later (an "exchange argument"). If you can't argue it, try DP.

Interval scheduling

Sort by end time, keep every interval that starts after the last kept one ends. Maximizes the number of non-overlapping intervals.

Merging intervals

Sort by start, extend the current interval while the next one overlaps.

Huffman coding

Repeatedly merge the two least frequent symbols (heap). Optimal prefix codes.

Coin change, careful

Taking the largest coin works for 1/2/5/10 coins but fails for 1/3/4 (6 = 3+3, greedy gives 4+1+1). Classic greedy trap.

Strings

KMP

O(n + m)

Precompute, for each prefix of the pattern, its longest proper prefix that is also a suffix; never re-scan text characters.

Rabin–Karp

O(n + m) average

Rolling hash: compare hashes of windows, verify on match. Great for many patterns or duplicate substrings.

Z-function

O(n)

For each position, the length of the longest match with the string's prefix. Search by running it on pattern + '$' + text.

Palindromes

O(n²) / O(n)

Expand around each center (2n−1 centers) is simple and usually enough; Manacher does it in O(n).

Anagrams & counts

O(n)

Compare letter-count arrays; slide a window and update counts in O(1) per step.

Math & bits

GCD (Euclid)

O(log min(a, b))

gcd(a, b) = gcd(b, a % b), and lcm = a / gcd · b.

Sieve of Eratosthenes

O(n log log n)

Cross out multiples of each prime starting at p². All primes up to n.

Fast exponentiation

O(log e)

Square the base, multiply in when the current bit of the exponent is 1. Do it mod m for huge powers.

Modular arithmetic

Take % m after every + and ×. Division mod a prime p: multiply by a^(p-2) mod p (Fermat).

Bit tricks

x & (x-1) drops the lowest set bit; x & -x keeps it; XOR of all numbers cancels pairs; masks 0 … 2ⁿ-1 enumerate subsets.

Backtracking

Build a solution step by step; when a partial solution can't work, undo the last choice and try the next. It's DFS over the tree of choices. The art is pruning: stop exploring a branch as early as possible. Typical uses: permutations, subsets, combinations summing to a target, N-Queens, Sudoku, word search.

Sketch the choice tree in the Sketch tab with a binary tree and capture a step per decision: it makes the recursion click.

Linear structures

Array & dynamic array Draw it

O(1) indexO(1)* appendO(n) insert in middle

Items side by side in memory. A dynamic array (JS array, Python list, Java ArrayList, C++ vector) doubles its capacity when full, so appends are cheap on average.

Pick it when you read by index or loop in order. It's the right default for almost every list: contiguous memory makes it very fast in practice.

Pick something else when you constantly insert or delete at the front or middle (deque, linked list) or search by value (hash set).

Linked list Draw it

O(1) insert at a known nodeO(n) find

Nodes that point to the next (and in a doubly linked list, the previous) node.

Pick it when you splice at positions you already hold a pointer to: LRU caches, free lists, merging sorted lists, undo histories.

Pick something else when you need indexing or fast iteration: an array is usually faster even for inserts on small lists.

Draw the pointers before you change them. Most linked-list bugs are lost next references.

Stack Draw it

O(1) push / popLIFO

Last in, first out. The call stack works this way.

Pick it when the most recent item matters first: undo, bracket matching, DFS, expression evaluation, monotonic-stack problems.

Pick something else when you need the oldest item first (queue).

Queue, deque & ring buffer Draw it

O(1) both endsFIFO

A queue serves in arrival order. A deque adds and removes at both ends. A ring buffer is a fixed-size array whose ends wrap around.

Pick it when you process in order: BFS, task queues, streaming buffers, sliding-window maximum (deque), last-N logs (ring buffer).

Pick something else when order depends on priority, not arrival (heap).

In JS, arr.shift() is O(n). For big queues, keep a head index instead.

Hashing

Hash map & hash set Draw it

O(1) avg get/putO(n) worstunordered

A hash function turns a key into a bucket index, so lookups jump straight to the right place. Collisions are handled with chains or probing.

Pick it when you look things up by key: counting, deduplication, caching, memoization, grouping, two-sum.

Pick something else when you need keys in sorted order or range queries (balanced tree), or memory is very tight.

Don't mutate an object while it's a key. In JS, plain objects turn keys into strings; use Map for real keys.

LRU cache

O(1) get/put

A hash map from key to node, plus a doubly linked list ordered by recent use. On access, move the node to the front; when full, drop the tail.

Pick it when you cache results with a size limit. A classic interview question that combines two structures.

In JS, a Map keeps insertion order, so delete-and-reinsert gives you a tiny LRU.

Bloom filter

O(k) checktiny memoryfalse positives

A bit array plus k hash functions. It can say "definitely not present" or "probably present".

Pick it when a cheap pre-check saves an expensive lookup: databases skipping disk reads, crawlers skipping seen URLs.

Pick something else when you need exact answers or deletions (use a hash set, or a counting Bloom filter).

Trees

Binary search tree & balanced trees Draw it

O(log n) balancedO(n) if degenerateordered

Smaller keys go left, larger right. Red-black and AVL trees rebalance themselves; that's what Java's TreeMap and C++'s std::map use.

Pick it when you need sorted order while inserting, or "floor/ceiling/next larger", or range queries.

Pick something else when you only need lookups by exact key (hash map, faster) or only the min/max (heap).

B-tree

O(log n)disk-friendly

A wide, shallow tree whose nodes hold many keys, so each disk or page read covers a lot of data.

Know it because nearly every database index (PostgreSQL, MySQL, SQLite) is a B-tree. It's why an index makes WHERE and ORDER BY fast.

Heap / priority queue

O(1) peekO(log n) push/popO(n) build

A complete binary tree stored in an array where every parent is ≤ its children (min-heap). Children of i are 2i+1 and 2i+2.

Pick it when you repeatedly need the smallest or largest: Dijkstra, schedulers, top-k, merging k sorted lists, running median.

Pick something else when you need to search for arbitrary items or iterate in order (balanced tree).

Trie (prefix tree)

O(L) per wordmemory-hungry

Each edge is a character; each path from the root spells a prefix.

Pick it when you query by prefix: autocomplete, spell checkers, word games, routing tables.

Pick something else when you only check whole words (hash set) or memory matters (sorted array + binary search).

Fenwick & segment trees

O(log n) query & update

Trees over array ranges. Fenwick (binary indexed) trees are tiny and do prefix sums; segment trees handle any associative operation (min, max, gcd…).

Pick it when range queries and point updates are interleaved, e.g. live leaderboards and competitive programming.

Pick something else when data never changes (plain prefix sums, O(1) per query).

Graphs & sets

Adjacency list See it

O(V + E) memory

For each node, the list of its neighbors (often a map from node to array).

Pick it when the graph is sparse, which real graphs (roads, social networks, dependencies) almost always are. BFS, DFS and Dijkstra all want this.

Adjacency matrix Draw it

O(1) edge checkO(V²) memory

A V×V table where cell [u][v] holds the edge (or its weight).

Pick it when the graph is small or dense, or you run Floyd–Warshall.

Pick something else when V is large: 100 000 nodes would need 10 billion cells.

Edge list

O(E) memory

Just a list of (u, v, weight). The format you'd paste into the Graph tab.

Pick it when you sort edges by weight (Kruskal) or read input; convert to an adjacency list for traversal.

Union-find (disjoint set)

≈ O(1) find & union

Each item points toward a group representative; path compression and union by size keep the trees flat.

Pick it when groups only merge, never split: Kruskal's MST, connected components, "are these accounts the same person?". See the template in Code templates.

Bitset

O(1) per bit1 bit per item

An integer or array of integers used as a set of flags.

Pick it when items are small integers: subsets in bitmask DP, permission flags, sieve of primes.

03Solving problems

Most problems are a known pattern in a costume. The process below gets you from "no idea" to working code without skipping the steps where bugs hide.

A process that works

  1. Restate the problem in your own words. Write down the input, the output, and the constraints (how big is n? can values be negative? duplicates? empty input?).
  2. Work two or three examples by hand, including an edge case: empty, one item, all equal, already sorted, negative numbers.
  3. Write the brute force first, even just in words, and state its cost. It's a correct baseline and often shows the waste.
  4. Find the bottleneck. What's repeated? Then look at the signals table below for a pattern that removes it.
  5. Check the budget. Use the n limit to pick the target complexity (n ≤ 10⁵ wants O(n log n) or better).
  6. Code it in small pieces with clear names. Get a simple version running before handling every edge case.
  7. Trace it. Step through your examples on paper or in the bench (the Your code tab shows every step()).
  8. Test the edges, then state the final time and space complexity.

Sliding window (longest valid window) Try it

function longest(s) {
  const count = new Map();
  let left = 0, best = 0;
  for (let right = 0; right < s.length; right++) {
    count.set(s[right], (count.get(s[right]) || 0) + 1);      // grow
    while (count.get(s[right]) > 1) {                         // invalid? shrink
      count.set(s[left], count.get(s[left]) - 1);
      left++;
    }
    best = Math.max(best, right - left + 1);
  }
  return best;   // longest substring without repeats
}

Prefix sums + hash map

// number of subarrays summing to k
function countK(nums, k) {
  const seen = new Map([[0, 1]]);
  let sum = 0, count = 0;
  for (const x of nums) {
    sum += x;
    count += seen.get(sum - k) || 0;
    seen.set(sum, (seen.get(sum) || 0) + 1);
  }
  return count;
}

Binary search on the answer

// smallest x in [lo, hi] where works(x)
// works must be false…false,true…true
function firstTrue(lo, hi, works) {
  while (lo < hi) {
    const mid = lo + Math.floor((hi - lo) / 2);
    if (works(mid)) hi = mid;
    else lo = mid + 1;
  }
  return lo;
}

Monotonic stack

// next greater element to the right
function nextGreater(a) {
  const res = Array(a.length).fill(-1);
  const stack = [];               // indices
  for (let i = 0; i < a.length; i++) {
    while (stack.length &&
           a[stack.at(-1)] < a[i])
      res[stack.pop()] = a[i];
    stack.push(i);
  }
  return res;
}

BFS on a grid Try it

function shortest(grid, sr, sc, er, ec) {
  const H = grid.length, W = grid[0].length;
  const dist = grid.map(r => r.map(() => -1));
  const q = [[sr, sc]]; dist[sr][sc] = 0;
  for (let h = 0; h < q.length; h++) {
    const [r, c] = q[h];
    if (r === er && c === ec) return dist[r][c];
    for (const [dr, dc] of [[1,0],[-1,0],[0,1],[0,-1]]) {
      const nr = r + dr, nc = c + dc;
      if (nr < 0 || nc < 0 || nr >= H || nc >= W) continue;
      if (grid[nr][nc] === '#' || dist[nr][nc] !== -1) continue;
      dist[nr][nc] = dist[r][c] + 1;     // mark when queued
      q.push([nr, nc]);
    }
  }
  return -1;
}

Union-find

const parent = [...Array(n).keys()];
const size = Array(n).fill(1);
function find(x) {
  while (parent[x] !== x) {
    parent[x] = parent[parent[x]]; // halve path
    x = parent[x];
  }
  return x;
}
function union(a, b) {
  a = find(a); b = find(b);
  if (a === b) return false;     // already linked
  if (size[a] < size[b]) [a, b] = [b, a];
  parent[b] = a; size[a] += size[b];
  return true;
}

Backtracking

function subsetsSumming(nums, target) {
  const out = [], pick = [];
  function go(i, sum) {
    if (sum === target) out.push([...pick]);
    if (sum >= target) return;         // prune
    for (let j = i; j < nums.length; j++) {
      pick.push(nums[j]);              // choose
      go(j + 1, sum + nums[j]);        // explore
      pick.pop();                      // undo
    }
  }
  go(0, 0);
  return out;
}

Memoized DP

// fewest coins to make amount (-1 if impossible)
function coins(cs, amount) {
  const memo = new Map();
  function f(a) {
    if (a === 0) return 0;
    if (a < 0) return Infinity;
    if (memo.has(a)) return memo.get(a);
    let best = Infinity;
    for (const c of cs) best = Math.min(best, f(a - c) + 1);
    memo.set(a, best);
    return best;
  }
  const r = f(amount);
  return r === Infinity ? -1 : r;
}

Fast & slow pointers

function hasCycle(head) {
  let slow = head, fast = head;
  while (fast && fast.next) {
    slow = slow.next;
    fast = fast.next.next;
    if (slow === fast) return true;
  }
  return false;
}

Algorithms are a small part of most software. These habits matter more day to day:

  • Model the data first. Good types and names make the code obvious; most bugs live in unclear data.
  • Small functions with one job, and keep side effects (I/O, network, database) at the edges so the core is easy to test.
  • Make illegal states unrepresentable: enums instead of magic strings, required fields instead of "maybe null".
  • Validate at the boundary (user input, API responses, files) and trust your types inside.
  • Draw it. A class or sequence diagram (UML section of the Sketch tab) exposes coupling and missing steps before you write code. See also Design patterns.
  • Measure before optimizing. Pick the right algorithm up front; micro-optimize only what a profiler shows.

04Design patterns

Named, proven answers to problems that keep recurring when you structure code. Learn them to recognize them and to talk about design, not to force them in: the simplest code that works is still the goal. Examples are TypeScript; draw them as class diagrams with the UML tools in Sketch. Each classic pattern links to Refactoring Guru, which has diagrams, analogies and code in many languages; its refactoring section covers code smells and how to fix them.

Principles first

Patterns are applications of a few principles. If you remember these, you can often derive the pattern yourself.

SOLID

Single responsibility: one reason to change. Open/closed: extend behavior without editing working code. Liskov: a subtype must work wherever its parent does. Interface segregation: small, focused interfaces. Dependency inversion: depend on abstractions, not concrete classes.

Composition over inheritance

Build behavior by combining small objects or functions instead of deep class trees. Inheritance couples you to the parent's internals; composition lets you swap parts.

KISS, YAGNI, DRY

Keep it simple. You aren't gonna need it: don't build for imagined futures. Don't repeat yourself, but wait for the third copy before abstracting: a wrong abstraction costs more than duplication.

Separation of concerns

Keep UI, business rules and I/O (database, network, files) apart. The core logic becomes easy to test and the edges easy to replace.

Creational patterns

How objects get made, so callers don't depend on exactly which class they get.

Factory Method Refactoring Guru

Problem: code is full of new ConcreteThing(), so adding a variant means editing every caller. Idea: one function decides which class to create.

function createShape(kind: 'circle' | 'square', size: number): Shape {
  switch (kind) {
    case 'circle': return new Circle(size);
    case 'square': return new Square(size);
  }
}

Use it when the concrete type depends on input or config (file parsers, payment providers, UI themes).

Skip it when there's only one implementation: just call the constructor.

Abstract Factory Refactoring Guru

Idea: one factory object creates a whole family of related objects that must match, e.g. lightTheme.button() and lightTheme.dialog().

Use it when products come in consistent families (UI themes, database drivers, platform widgets).

Skip it when there is only one family or one product: a plain factory function is enough.

Builder Refactoring Guru

Problem: constructors with many optional parameters. Idea: set parts step by step, then build().

const req = new RequestBuilder('/api/users')
  .method('POST')
  .header('Authorization', token)
  .json({ name: 'Ada' })
  .build();

Use it when objects have many optional parts or must be validated before use (queries, HTTP requests, test data).

Skip it when an options object { ... } with defaults is enough, which in JS/TS it usually is.

Singleton Refactoring Guru

Idea: exactly one instance, reachable from anywhere (a config, a logger, a connection pool).

Be careful: it's hidden global state that makes testing hard. Prefer creating one instance at startup and passing it in (dependency injection). A module-level export const db = … is the JS equivalent.

Prototype Refactoring Guru

Idea: create new objects by copying an existing one (structuredClone, {...obj}, copy()).

Use it when setting up an object is expensive and copies differ only a little (game entities, document templates).

Structural patterns

How objects fit together into bigger structures.

Adapter Refactoring Guru

Problem: a library's interface doesn't match the one your code expects. Idea: a thin wrapper that translates.

interface PaymentGateway { pay(eur: number): Promise<void> }

class LegacyPayAdapter implements PaymentGateway {
  constructor(private legacy: LegacyPayClient) {}
  pay(eur: number) {
    return this.legacy.sendPayment({ cents: Math.round(eur * 100) });
  }
}

Use it when integrating third-party code or replacing a vendor: the rest of your app never sees the vendor's API.

Bridge Refactoring Guru

Problem: two independent dimensions multiply subclasses (RedCircle, BlueSquare…). Idea: split them into two hierarchies and connect them with a reference: a Shape holds a Renderer.

Use it when abstraction and implementation should vary separately (remote controls and devices, shapes and rendering backends).

Decorator Refactoring Guru

Idea: wrap an object or function to add behavior (logging, caching, retries) without changing it.

const withLogging = <A extends unknown[], R>(fn: (...a: A) => R) =>
  (...args: A): R => {
    console.log('calling', fn.name, args);
    return fn(...args);
  };
const loggedFetchUser = withLogging(fetchUser);

Use it when you want to stack optional behaviors. Middleware in Express/Hono is this pattern.

Facade Refactoring Guru

Idea: one simple interface in front of a complicated subsystem, e.g. video.convert(file, 'mp4') hiding codecs, buffers and muxers.

Use it when callers only need a few common operations of a big library.

Composite Refactoring Guru

Idea: treat a group the same as a single item: a folder and a file both have size(); a folder sums its children.

Use it when you have trees: file systems, UI component trees, menus, organization charts.

Proxy Refactoring Guru

Idea: a stand-in with the same interface that controls access: lazy loading, caching, permission checks, remote calls.

JS has a built-in Proxy; Vue's reactivity is built on it.

Flyweight Refactoring Guru

Idea: share the heavy, unchanging part of many similar objects (a tree's mesh and texture) and store only the small per-object state (position) separately.

Use it when you have huge numbers of similar objects and memory runs out: particles, map tiles, characters in a text editor.

Behavioral patterns

How objects share work and talk to each other.

Strategy Refactoring Guru

Problem: a growing if/else over ways of doing one thing. Idea: make each way a separate function or object and pass in the one you want.

type Pricing = (total: number) => number;
const regular: Pricing = t => t;
const student: Pricing = t => t * 0.8;

function checkout(total: number, pricing: Pricing) {
  return pricing(total);
}

Use it when behavior varies by user choice or config: sorting orders, pricing rules, compression, route finding. The bench's algorithm dropdowns are strategies.

Observer (pub/sub) Refactoring Guru

Idea: subscribers register with a subject and get notified on changes; the subject doesn't know who they are.

class Emitter<T> {
  private fns = new Set<(v: T) => void>();
  on(fn: (v: T) => void) {
    this.fns.add(fn);
    return () => this.fns.delete(fn);   // unsubscribe
  }
  emit(v: T) { this.fns.forEach(fn => fn(v)); }
}

Use it when several parts react to one event: DOM events, UI state stores, WebSocket messages.

Always unsubscribe, or listeners leak memory and fire on dead components.

Command Refactoring Guru

Idea: wrap an action as an object with do() and undo() so you can queue, log, replay or undo it.

interface Command { do(): void; undo(): void }
const history: Command[] = [];
function run(cmd: Command) { cmd.do(); history.push(cmd); }
function undo() { history.pop()?.undo(); }

Use it when you need undo/redo, job queues or macros.

Memento Refactoring Guru

Idea: save snapshots of state to restore later, without exposing internals.

The Sketch tab's undo and its captured steps are mementos: each one is a saved copy of the board.

State (state machine) Refactoring Guru

Idea: list the states and the allowed transitions explicitly, instead of juggling boolean flags.

const next = {
  idle:    { fetch: 'loading' },
  loading: { ok: 'done', fail: 'error' },
  error:   { retry: 'loading' },
  done:    {},
} as const;

Use it when something has modes with rules: orders, network requests, game characters, form wizards. Draw it first!

Iterator Refactoring Guru

Idea: walk through a collection without knowing how it's stored. Built into most languages: for…of plus generators in JS, __iter__ in Python.

Template Method Refactoring Guru

Idea: a base routine fixes the steps; subclasses (or passed-in functions) fill in specific steps, e.g. export() = header() + rows() + footer().

Often better: pass the varying steps as functions (strategy) instead of subclassing.

Chain of Responsibility Refactoring Guru

Idea: pass a request along a chain of handlers until one deals with it. HTTP middleware, event bubbling and validation pipelines work this way.

Mediator Refactoring Guru

Idea: components stop talking to each other directly and talk through one mediator, e.g. form fields notify the form, which decides what to enable.

Use it when many objects interact in tangled ways (dialogs, chat rooms, air-traffic-control style coordination).

Don't let the mediator grow into a god object.

Visitor Refactoring Guru

Idea: add new operations over a fixed set of node types without editing those types: each node calls visitor.visitX(this).

Use it when the types rarely change but operations keep being added: compilers walking syntax trees, exporters, linters.

Skip it when types change often. In TS, a discriminated union with a switch is usually simpler.

Architecture patterns

Patterns at the scale of a whole app.

Dependency injection

Idea: pass collaborators in instead of creating them inside. Production gets real ones, tests get fakes.

class SignupService {
  constructor(private users: UserRepo, private mail: Mailer) {}
}
new SignupService(new PgUserRepo(db), new SmtpMailer(cfg)); // app
new SignupService(new MemoryUserRepo(), new FakeMailer());  // test

Spring, ASP.NET, NestJS and Angular have DI containers; plain constructor parameters work fine too.

Repository

Idea: hide data access behind an interface like users.byId(id) / users.save(u), so business logic doesn't contain SQL.

Use it when logic is non-trivial and you want to test it without a database.

Skip it when the app is simple CRUD: the ORM already is your repository.

MVC, MVVM & components

Model (data and rules), View (what's shown), and a Controller or ViewModel connecting them. Rails, Django, Laravel and Spring MVC use MVC; modern frontends use components with state stores, which is the same separation at a smaller scale.

Layered, clean & hexagonal

Business rules in the center; the database, web framework and external APIs are plug-ins at the edges, connected through interfaces (ports and adapters).

Use it when the domain is complex and long-lived.

Skip it when it's a small app: the layers become ceremony.

Event-driven

Parts communicate by publishing events ("OrderPlaced") rather than calling each other. Built with queues or logs (RabbitMQ, Kafka).

Use it when work is slow or should happen independently (emails, analytics, notifications).

Harder to trace and debug; events can arrive twice or out of order, so make handlers idempotent.

Modular monolith vs microservices

Start with a modular monolith: one deployable app with clear internal modules. Split out services only when a part needs to scale, deploy or be owned separately. Microservices trade code complexity for network and operations complexity.

Anti-patterns to recognize

  • God object: one class that knows and does everything. Split it by responsibility.
  • Premature abstraction: interfaces, factories and layers for code that has exactly one use. Wait until a second or third real case shows the shape.
  • Pattern-itis: using a pattern because it exists. If a plain function does the job, use the function.
  • Shotgun surgery: one small change forces edits in many files. Related logic is scattered; pull it together.
  • Primitive obsession: passing raw strings and numbers for things that deserve a type (Email, Money, UserId).
  • Singleton everywhere: global state that makes order of initialization and tests fragile.

Languages

Python

Readable, batteries included, the lingua franca of data and AI. Modern tooling: uv for packages and environments, Ruff for linting and formatting.

Pick it when you do data analysis, ML/AI, scripting and automation, or quick backends (Django, FastAPI). Great first language.

Pick something else when CPU-heavy loops dominate (Go, Rust, C++), you build mobile apps (Swift, Kotlin) or code runs in the browser (TypeScript).

JavaScript / TypeScript

The only language browsers run natively, and with Node, Bun or Deno a full server language too. TypeScript adds static types and is the norm for anything beyond a script.

Pick it when anything runs in a browser, you want one language across frontend and backend, or you deploy to serverless/edge platforms.

Pick something else when you need raw number crunching (Python with NumPy, Rust) or systems-level control (Rust, C++).

Java

Fast JVM, strong typing, huge ecosystem. Modern Java (records, pattern matching, virtual threads) is far less verbose than its reputation.

Pick it when you build large, long-lived backends (Spring), work in enterprise or banking, or want a widely hired skill.

Pick something else when you want concise syntax on the JVM (Kotlin), tiny single-binary services (Go), or quick scripts (Python).

Kotlin

Concise, null-safe JVM language, fully interoperable with Java.

Pick it when you build Android apps (the default), JVM backends with less boilerplate (Spring, Ktor), or want to share logic between Android and iOS (Kotlin Multiplatform).

Pick something else when your team and libraries live outside the JVM world.

C#

.NET's language: excellent tooling, fast runtime, runs on Windows, macOS and Linux.

Pick it when you make Unity games, Windows desktop apps, or ASP.NET Core backends, or join a .NET company.

Pick something else when your team is on the JVM (Java/Kotlin) or JS stack already: they're in the same niche.

Go

Small language, fast compiles, easy concurrency with goroutines, deploys as one static binary. Docker and Kubernetes are written in it.

Pick it when you write network services, CLIs, DevOps and cloud tooling, or want something simple a team can learn in a week.

Pick something else when you need UIs, data science (Python), or maximum performance without a garbage collector (Rust).

Rust

C/C++-level speed with memory safety enforced at compile time. The most admired language in Stack Overflow's survey for years running.

Pick it when performance and correctness both matter: systems code, CLIs, WebAssembly, high-throughput services, replacing C/C++.

Pick something else when you need to prototype quickly or the team is new to it under a deadline: the borrow checker has a real learning curve.

C / C++

Maximum control over memory and hardware; decades of libraries.

Pick it when you do embedded, operating systems, game engines (Unreal), audio/graphics, competitive programming (C++ STL), or extend an existing C/C++ codebase.

Pick something else when you start a new systems project and safety matters (Rust), or build web apps.

Swift

Apple's modern, safe language for iOS, macOS, watchOS and visionOS.

Pick it when the app is Apple-only or needs the best platform integration.

Pick something else when you must ship on Android too with one team (Flutter, React Native, Kotlin Multiplatform).

Dart

The language of Flutter; easy for anyone who knows Java, C# or TypeScript.

Pick it when you build with Flutter.

Pick something else when you're outside Flutter: its server and tooling ecosystem is small.

PHP

Powers a large share of the web (WordPress). Modern PHP 8 is typed and fast.

Pick it when you build on WordPress or Laravel, or need cheap shared hosting.

Pick something else when the work isn't web, or you want one language from browser to server (TypeScript).

Ruby

Expressive language, best known for Rails.

Pick it when you want to build a CRUD product very quickly with Rails conventions.

Pick something else when you need a large hiring pool or heavy computation.

Elixir

Functional language on the Erlang VM, built for huge numbers of concurrent, fault-tolerant processes. Its Phoenix framework is the most admired web framework in Stack Overflow's 2025 survey.

Pick it when the app is real-time and connection-heavy: chat, live dashboards, multiplayer, IoT.

Pick something else when you need a big hiring pool or CPU-heavy number crunching.

Zig

A small, modern C alternative with explicit memory handling and excellent C interop. Still pre-1.0, so expect breaking changes.

Pick it when you want to learn low-level programming with less complexity than C++, or need a better C toolchain (Zig can compile C).

Pick something else when you need stability and a big library ecosystem today (C, C++, Rust).

SQL

Not optional: almost every application stores data in a relational database.

Learn it regardless of stack: SELECT with JOIN, GROUP BY, indexes, transactions, and how to read a query plan (EXPLAIN).

Frontend & web frameworks

Plain HTML, CSS & JavaScript

The platform itself: semantic HTML, flexbox/grid and the DOM. This bench is built without a framework.

Pick it when you build small sites, widgets, prototypes, or learn the fundamentals every framework builds on.

Pick something else when the UI has lots of shared state and many screens (a component framework).

React

The most used component library, with the biggest ecosystem and job market. Use it through a framework (Next.js, React Router, TanStack Start) or as a single-page app with Vite. The TanStack libraries (Query, Router, Table, Form) are a common companion.

Pick it when you want the safest bet for jobs and libraries, or build complex interactive UIs. A React + Vite SPA is the simplest setup for apps behind a login.

Pick something else when the site is mostly content (Astro), or you want less boilerplate (Svelte, Vue).

Next.js

The most used full-stack React framework: server rendering, static generation, Server Components, API routes. Smoothest on Vercel.

Pick it when pages must rank in search and stay dynamic (stores, marketplaces, social), or you want the most documented React stack.

Pick something else when it's an app behind a login with no SEO (React + Vite), mostly content (Astro), or you want a simpler data model (React Router, TanStack Start). Satisfaction has dipped as its caching and server/client rules grew complex.

React Router v7 (formerly Remix)

Remix merged into React Router: loaders and actions built on web standards, from a plain SPA up to full server rendering.

Pick it when you want full-stack React with simple, web-standard data loading, or you already use React Router and want to grow into SSR.

Pick something else when you want the largest ecosystem and hosting integrations (Next.js).

TanStack Start

A newer full-stack React framework on TanStack Router and Vite, focused on end-to-end type-safe routing and data loading. Client-first, with server functions and SSR.

Pick it when you build dashboards and app-like UIs in TypeScript and value type safety and Vite's speed.

Pick something else when you're a beginner relying on tutorials, or need React Server Components today (Next.js). Check its current release status before betting a big project on it.

Vue + Nuxt

Approachable component framework with single-file components and excellent docs; Nuxt adds routing, SSR and server routes.

Pick it when you want a gentle learning curve with a mature ecosystem, or join a Vue team (popular in Europe and Asia).

Pick something else when the job market in your area is React-dominated.

Svelte + SvelteKit

Compiles components into small, fast JavaScript with very little boilerplate; SvelteKit is the full-stack framework.

Pick it when you want the most enjoyable, least-code way to build fast apps and sites; consistently near the top in developer satisfaction.

Pick something else when you need the biggest pool of libraries and developers (React).

Angular

Batteries-included and opinionated: TypeScript, dependency injection, router, forms and signals built in.

Pick it when large enterprise teams need one consistent way of doing everything.

Pick something else when the project is small, content-focused, or you're just starting out.

Astro

Content-first framework that ships zero JavaScript by default and hydrates interactive "islands" only where needed, with components from React, Vue, Svelte or Solid.

Pick it when you build blogs, docs, portfolios and marketing sites that should load instantly and rank well.

Pick something else when the whole page is an interactive app (Next.js, SvelteKit, TanStack Start).

HTMX (and Hotwire, Livewire)

Add interactivity with HTML attributes; the server returns HTML fragments instead of JSON. Pairs with any backend (Django, Rails, Laravel, Go).

Pick it when a server-rendered app needs some dynamic behavior and you'd rather not maintain a separate JS frontend.

Pick something else when the UI has rich client-side state: editors, offline mode, drag-and-drop heavy apps.

Tailwind CSS

Utility classes in your markup. Often paired with copy-in component kits like shadcn/ui.

Pick it when you want fast, consistent styling in a component-based app.

Pick something else when you prefer semantic CSS or the site is tiny: plain CSS with custom properties is enough.

Vite (build tools)

The standard dev server and bundler for modern frontends; Vue, Svelte, React SPAs and TanStack Start build on it.

Pick it when you start any new frontend that doesn't come with its own toolchain.

Pick something else when you maintain an existing webpack setup that works: migrate only when it hurts.

Backend & runtimes

Node.js

The default JavaScript runtime: by far the most used, with the broadest package compatibility.

Pick it when you want the safe, boring JS backend choice, or depend on native npm packages.

Pick something else when you want an all-in-one fast toolchain (Bun) or secure-by-default scripts (Deno).

Bun

A fast JS runtime that is also a package manager, bundler and test runner; largely Node-compatible.

Pick it when you start a new TypeScript project and want speed and fewer tools to configure.

Pick something else when you rely on native Node addons or a conservative production environment (Node).

Deno

A runtime with TypeScript, formatter, linter and test runner built in, and permissions off by default.

Pick it when you write scripts and small services and like strong security defaults and zero config.

Pick something else when you need maximum npm compatibility (Node).

Express & Fastify

Minimal Node web frameworks. Express has the most tutorials; Fastify is faster and validates with schemas.

Pick it when you want a straightforward JS API server on Node. Prefer Fastify for new projects.

Pick something else when you deploy to edge/serverless (Hono) or a big team needs enforced structure (NestJS).

Hono

A tiny, fast framework built on web standards that runs on Node, Bun, Deno, Cloudflare Workers and other edge platforms.

Pick it when you build APIs for serverless/edge, or want one codebase that runs on any runtime.

Pick something else when a large team wants modules, DI and conventions (NestJS).

NestJS

Structured TypeScript backend framework with modules, decorators and dependency injection (Angular-like).

Pick it when a larger team builds a long-lived TS backend and wants Spring-style structure.

Pick something else when the service is small: the ceremony isn't worth it (Fastify, Hono).

Django

Python's batteries-included framework: ORM, migrations, admin panel, auth, forms.

Pick it when you build a database-backed product with an admin and user accounts, fast.

Pick something else when you only need a small typed JSON API or ML endpoint (FastAPI).

FastAPI

Modern Python API framework built on type hints and Pydantic: validation and OpenAPI docs come for free. Its usage has grown quickly.

Pick it when you build JSON APIs, serve ML/AI models, or want async Python.

Pick something else when you want an admin panel, auth and templates built in (Django).

Flask

Minimal Python web framework; you add what you need.

Pick it when it's a tiny service or a learning project.

Pick something else when you start a real API today (FastAPI) or a full app (Django).

Spring Boot

The Java/Kotlin standard: dependency injection, data access, security, messaging, observability.

Pick it when you build enterprise systems with large teams, or work where the JVM is the standard.

Pick something else when you want a light, fast-starting tiny service (Go) or quick prototype (Rails, Django).

ASP.NET Core

Fast, well-documented C# framework for APIs and web apps (Razor Pages, Blazor).

Pick it when your team knows C#, or you build on Azure or Windows-centric infrastructure.

Pick something else when the team is on another stack: it overlaps with Spring.

Laravel

PHP's productive full-stack framework, with first-party tools for queues, auth, payments and Livewire for interactivity.

Pick it when you want to ship a web product quickly in PHP, with cheap hosting.

Pick something else when you want one language with your JS frontend (Node, Next.js).

Ruby on Rails

Convention over configuration; Hotwire for interactivity without a JS framework.

Pick it when a small team wants maximum speed building a CRUD/SaaS product.

Pick something else when you need a large hiring pool or very high throughput.

Phoenix (Elixir)

Web framework on the Erlang VM; LiveView builds real-time UIs rendered from the server.

Pick it when real-time features and many simultaneous connections are central.

Pick something else when you need to hire quickly or reuse a JS/Java ecosystem.

Go (net/http, chi, Gin, Echo)

Go's standard library alone can serve production HTTP; small routers add convenience.

Pick it when you build high-throughput services or microservices that should be simple to run (one binary, low memory).

Pick something else when you want an admin, ORM and auth out of the box (Django, Rails, Laravel).

Rust (Axum, Actix Web)

Very fast, memory-safe web servers.

Pick it when latency, throughput or memory are critical, or the rest of the system is Rust.

Pick something else when you need to iterate quickly on business features (Go, Node, Python).

Supabase

Open-source backend-as-a-service on PostgreSQL: database, auth, storage, realtime, edge functions and pgvector.

Pick it when you want a real Postgres database with auth and APIs without writing a backend; good for MVPs, mobile and side projects.

Pick something else when business logic is complex and belongs in your own server, or you want to avoid platform-specific features.

Firebase

Google's backend-as-a-service: Firestore (NoSQL), auth, push notifications, hosting, strong mobile SDKs.

Pick it when you build mobile apps that need auth, sync and push fast.

Pick something else when data is relational or you need complex queries (Supabase or PostgreSQL).

Mobile

SwiftUI (native iOS)

Apple's declarative UI framework.

Pick it when the app is iOS-only, or deep platform features matter most (widgets, Watch, AR, background tasks).

Pick something else when you need Android too and have one team (Flutter, React Native, Kotlin Multiplatform).

Jetpack Compose (native Android)

Android's modern declarative UI toolkit, in Kotlin.

Pick it when the app is Android-only or needs the best Android integration.

React Native + Expo

React components rendered with real native views. Expo is now the recommended way to build with React Native (routing, builds, over-the-air updates).

Pick it when a web/React team builds its first mobile app, or you want to share logic and people with a React web app.

Flutter

Google's toolkit, written in Dart, which draws every pixel itself: identical UI on iOS, Android, web and desktop.

Pick it when you want one codebase with a custom, highly polished, animation-rich design, or you're starting fresh with no web background.

Kotlin Multiplatform & Compose Multiplatform

Share Kotlin business logic across Android, iOS, desktop and web while keeping native UI, or share the UI too with Compose Multiplatform (stable on Android, iOS and desktop; web in beta).

Pick it when you have Android/Kotlin developers, or want to share logic gradually inside existing native apps.

Pick something else when your team is web-first (Expo) or you want one mature UI toolkit everywhere today (Flutter).

Progressive Web App

A website that installs to the home screen and works offline (this bench is one).

Pick it when the app is content, forms or tools, you want zero app-store friction, and one codebase for every device.

Pick something else when you need deep device features, background work or app-store presence (native or cross-platform).

Capacitor (Ionic)

Microsoft's cross-platform UI for C#, successor to Xamarin.

Chromium plus Node.js: a web app shipped as a desktop app. Behind VS Code, Slack and Discord.

Web frontend with a Rust backend, using the operating system's own webview. Installers are a few MB instead of 100+; Tauri 2 also targets iOS and Android.

Pick it when you start a new, lean desktop app with web tech, or want desktop and mobile from one codebase.

WPF / WinUI (.NET)

Native Windows UI frameworks for C#.

Pick it when the app is Windows-only (internal business tools, utilities) and the team knows C#.

Pick something else when you need macOS or Linux too (Avalonia, Tauri, Qt).

Avalonia

Cross-platform XAML UI for .NET (Windows, macOS, Linux, plus mobile and browser).

Pick it when a C# team wants a WPF-like toolkit on every desktop OS.

Qt

Mature cross-platform toolkit in C++, also usable from Python (PySide).

Pick it when you build performance-sensitive or embedded GUIs, scientific and CAD tools, or Python desktop apps.

Pick something else when licensing for closed-source commercial use is a concern (check Qt's licenses) or the team is web-first.

SwiftUI / AppKit (macOS)

Apple's native frameworks for Mac apps.

Pick it when the app is Mac-only and should feel completely at home on macOS.

Pick something else when Windows users matter.

Compose Multiplatform (desktop)

Kotlin's declarative UI on Windows, macOS and Linux (JVM).

Pick it when a Kotlin team wants to share UI between Android and desktop.

Pick something else when app size matters: it ships a JVM runtime.

Databases & data stores

PostgreSQL

The most used and most admired database among developers (Stack Overflow 2025). Relational, strict and correct, with JSON, full-text search and extensions (pgvector, PostGIS, TimescaleDB).

Pick it when you're not sure: it's the safe default for almost any application, and it can cover documents, search and vectors until you outgrow them.

Pick something else when the database should live inside the app (SQLite), you need sub-millisecond caching (Redis), or analytics over billions of rows (ClickHouse).

MySQL / MariaDB

Widely hosted relational databases, simple to operate, common with PHP stacks.

Pick it when your host or team already standardizes on it (WordPress, Laravel, many shared hosts).

Pick something else when you start fresh and want richer features (PostgreSQL).

SQLite

A full SQL database in a single file, embedded in your app, with no server.

Pick it when data lives on the device (mobile, desktop, CLI), for tests and prototypes, or for small sites with one server.

Pick something else when many servers write at once (PostgreSQL), or you need it replicated at the edge (Turso, D1).

Turso / Cloudflare D1 (edge SQLite)

Managed SQLite replicated close to users, one of the fastest-growing database categories.

Pick it when you run on edge platforms and want low-latency reads worldwide, or many small databases (one per user or tenant).

Pick something else when you need heavy concurrent writes or mature extensions (PostgreSQL).

Managed Postgres: Neon, Supabase and cloud offerings

PostgreSQL without running servers. Neon is serverless (scales to zero, database branches for every pull request); Supabase adds auth, storage and APIs; AWS, Google and Azure have their own.

Pick it when you want Postgres and don't want to manage backups, upgrades and scaling.

Pick something else when cost at large steady load favors your own servers.

MongoDB

Document database storing JSON-like records; flexible schema, scales horizontally.

Pick it when data is naturally document-shaped (catalogs, content, event payloads) and rarely joined.

Pick something else when data has many relationships or needs strict consistency across records (PostgreSQL). "Schemaless" still needs a schema in your code.

Redis / Valkey

In-memory key-value store with rich data types. Valkey is the open-source fork maintained under the Linux Foundation.

Pick it when you need caching, sessions, rate limiting, queues, pub/sub or leaderboards.

Pick something else when it would be your main source of truth: use a durable database and Redis beside it.

DynamoDB / Firestore

Fully managed NoSQL databases from AWS and Google that scale automatically.

Pick it when access patterns are known up front and you want zero operations at any scale, inside that cloud.

Pick something else when queries are ad hoc or relational, or you want to stay portable (PostgreSQL).

Elasticsearch / OpenSearch

Distributed full-text search and log analytics engines.

Pick it when you need powerful search over large data, or log/observability analytics.

Pick something else when search is simple (PostgreSQL full-text) or you want easy instant search for an app (Meilisearch, Typesense).

Meilisearch / Typesense

Lightweight search engines with typo tolerance and instant results, easy to run.

Pick it when you add search-as-you-type to a product or documentation site.

Pick something else when you need heavy analytics or petabyte scale (Elasticsearch/OpenSearch).

ClickHouse

Columnar database for very fast analytics over huge event tables.

Pick it when you build product analytics, logs or metrics dashboards over billions of rows.

Pick something else when data fits on a laptop (DuckDB) or you need transactional updates (PostgreSQL).

DuckDB

An in-process analytics database: SQL over CSV, Parquet and dataframes, no server.

Pick it when you analyze data locally or in a pipeline: often faster and simpler than pandas for big files.

Pick something else when many users write concurrently (PostgreSQL) or data is distributed (ClickHouse, Spark).

pgvector

Vector similarity search inside PostgreSQL, used for RAG and semantic search. A strong trend is keeping vectors in Postgres rather than adding a separate database.

Pick it when you add AI search to an app that already uses Postgres, up to many millions of vectors.

Pick something else when vectors are the core product at very large scale (a dedicated vector database).

Dedicated vector databases (Qdrant, Weaviate, Pinecone)

Databases built only for embedding search, with advanced filtering and scaling.

Pick it when vector search is central, very large, or needs features Postgres lacks.

Pick something else when you're just adding semantic search to an existing app (pgvector).

Neo4j (graph databases)

Stores nodes and relationships; queries walk connections (Cypher).

Pick it when questions are about paths and connections: recommendations, fraud rings, knowledge graphs.

Pick something else when relationships are simple: SQL joins or recursive queries handle them.

TimescaleDB (time series)

A PostgreSQL extension for time-stamped data: sensor readings, metrics, prices.

Pick it when you store lots of time series and want to keep SQL and Postgres.

Pick something else when it's pure metrics monitoring (Prometheus) or huge event analytics (ClickHouse).

ORMs and query builders

Drizzle, Prisma (TypeScript), SQLAlchemy (Python), Hibernate/JPA (Java), Entity Framework Core (C#).

Pick one when you want type-safe queries and migrations. Drizzle stays close to SQL; Prisma has a friendly schema language.

Write SQL directly when queries are complex or performance-critical. Always look at the SQL an ORM generates.

AI & machine learning

LLM APIs (Claude, OpenAI, Gemini)

Call a hosted model through the provider's SDK: chat, summarization, extraction, tool use.

Pick it when you add AI features to an app. Start with a direct SDK call: it's the simplest thing that works, and you can add a framework later.

Pick something else when data can't leave your machines (local models) or you need a multi-step agent loop (an agent SDK).

Vercel AI SDK

TypeScript toolkit for streaming chat UIs, structured output, tool calling and agents across many model providers, with MCP support.

Pick it when you build AI features inside a TypeScript/React web app and want provider flexibility.

Pick something else when you need long-running durable workflows (LangGraph) or Python (PydanticAI).

Claude Agent SDK

The agent loop behind Claude Code as a library (TypeScript and Python): built-in file, shell and web tools, subagents, and deep MCP integration.

Pick it when you build agents that work with files, code and commands, or want a capable agent with little scaffolding.

Pick something else when you need a fixed, auditable pipeline (LangGraph) or to switch between model providers (Vercel AI SDK, PydanticAI).

LangGraph

Build agents as explicit graphs of steps with state, checkpoints and human-in-the-loop.

Pick it when workflows are complex, long-running or must resume after failures.

Pick something else when a simple chat or single tool loop will do: it's overkill there.

PydanticAI

Typed Python agent framework from the Pydantic team; validated structured outputs and dependency injection.

Pick it when you build Python agents and want type safety and testability, especially with FastAPI.

Pick something else when you work in TypeScript (Vercel AI SDK).

Model Context Protocol (MCP)

An open protocol for giving AI assistants tools and data. Write an MCP server once and Claude, IDEs and agent frameworks can all use it.

Pick it when you want AI assistants to use your API, database or service.

Skip it when the tool lives only inside your own app's code: plain function/tool calling is simpler.

Local models (Ollama, llama.cpp)

Run open-weight models on your own machine or server.

Pick it when privacy, offline use or cost per call matters, or for experimenting.

Pick something else when you need the strongest reasoning and coding quality (frontier hosted models).

PyTorch

The standard deep-learning framework in research and industry.

Pick it when you train or fine-tune neural networks: vision, language, audio.

Pick something else when data is tabular (scikit-learn, gradient boosting) or you only call a model API.

scikit-learn & gradient boosting

Classic ML (regression, classification, clustering) plus XGBoost/LightGBM for tabular data.

Pick it when you predict from spreadsheet-like data: gradient boosting usually beats neural nets there.

Pick something else when inputs are images, audio or free text (PyTorch, pre-trained models).

Hugging Face

Hub of open models and datasets, plus the Transformers library.

Pick it when you want a pre-trained model to use or fine-tune instead of training from scratch.

pandas & Polars (in Jupyter)

DataFrame libraries for cleaning and analyzing tables; Jupyter notebooks for exploring. Polars is a much faster, Rust-based newer alternative.

Pick it when you explore and analyze data. Use Polars for new work on larger data; pandas has the most tutorials and integrations.

Pick something else when the data doesn't fit in memory (DuckDB, Spark).

Apache Spark / Databricks

Distributed processing across a cluster.

Pick it when data really is too big for one machine (terabytes and more).

Pick something else when it fits on one machine: DuckDB or Polars will be simpler and often faster.

dbt + orchestrators (Dagster, Airflow)

dbt turns SQL into tested, versioned data transformations; orchestrators schedule pipelines.

Pick it when you build a data warehouse or recurring ETL pipelines.

Pick something else when it's a one-off analysis (a notebook).

Tooling, infra & hosting

Git & GitHub / GitLab

Version control and collaboration: branches, pull requests, code review.

Always. Small commits, clear messages, review before merging.

Docker & Compose

Package an app with its environment so it runs the same everywhere. Used by about 7 in 10 developers (Stack Overflow 2025).

Pick it when you deploy servers, run databases locally (Compose), or want reproducible builds.

Pick something else when a platform builds and runs your code for you (Vercel, Netlify, Cloudflare).

Kubernetes

Runs and scales containers across many machines.

Pick it when you run many services with real scaling and reliability needs, and have people to operate it.

Pick something else when it's one app or a small team: a PaaS or a single server with Docker is far simpler.

CI/CD (GitHub Actions, GitLab CI)

Run tests, linters and deployments automatically on every push.

Pick it when more than one person touches the code, or you ever forget to run tests. (Always.)

Terraform / OpenTofu

Describe cloud infrastructure in code you can review and version. OpenTofu is the open-source fork.

Pick it when you manage real cloud resources that must be reproducible.

Pick something else when a PaaS handles infrastructure for you.

AWS, Azure, Google Cloud

The big clouds: compute, storage, managed databases, queues, identity. AWS is the largest; Azure fits Microsoft shops; Google Cloud is strong in data and ML.

Pick it when you need many managed services, compliance, or large scale.

Pick something else when it's a side project or small product: a PaaS is cheaper in time.

Vercel & Netlify

Push-to-deploy platforms for frontends and serverless functions; Vercel is made by the Next.js team.

Pick it when you deploy Next.js, Astro, SvelteKit and similar with previews for every pull request.

Pick something else when you run long-lived servers, WebSockets or heavy background jobs (Fly.io, Render, a VPS).

Cloudflare (Workers, Pages, R2, D1)

Code that runs at the edge in hundreds of locations, plus storage and databases.

Pick it when you want low latency worldwide and generous free tiers; great with Hono.

Pick something else when you need full Node compatibility or long-running processes.

Fly.io, Render, Railway

Platforms that run your Docker container or app server with databases attached.

Pick it when you have a backend server (Django, Rails, Go, Phoenix) and don't want to manage machines.

Pick something else when the site is static (GitHub Pages, Netlify).

A plain VPS

Rent a Linux server (Hetzner, DigitalOcean and many others) and run Docker on it.

Pick it when you want the lowest cost and to learn Linux and operations.

Pick something else when you don't want to handle security updates, backups and uptime yourself.

Observability (OpenTelemetry, Grafana, Sentry)

Logs, metrics, traces and error tracking for production.

Pick it when real users depend on the app. Start with error tracking (Sentry), then add metrics.

uv & Ruff (Python tooling)

uv replaces pip, venv and pyenv with one very fast tool; Ruff replaces Flake8, isort and Black. Both are Rust-based and among the most admired developer tools.

Pick them for every new Python project.

ESLint + Prettier, or Biome

Linting and formatting for JS/TS. Biome is one fast tool that does both.

Pick Biome for new projects that want speed and less config; ESLint when you need its huge plugin ecosystem.

npm, pnpm, Yarn, Bun

JavaScript package managers.

Pick pnpm for fast, disk-efficient installs and monorepos; npm for zero setup; bun install if you use Bun.

APIs & testing

REST (+ OpenAPI)

Resources over HTTP with standard verbs and status codes.

Pick it when you build public APIs or have many different clients: simple, cacheable, universal.

Pick something else when one TS team owns both ends (tRPC) or clients need flexible nested data (GraphQL).

GraphQL

Clients ask for exactly the fields they need from one endpoint.

Pick it when several frontends need different shapes of deeply related data.

Pick something else when the API is simple: caching, authorization and performance are harder than with REST.

tRPC (and typed server functions)

Call backend functions from the frontend with shared TypeScript types and no schema files.

Pick it when one team owns a TypeScript frontend and backend in one repo.

Pick something else when other languages or third parties consume the API (REST).

gRPC

Fast, typed binary RPC between services using Protocol Buffers.

Pick it when internal services in different languages talk a lot.

Pick something else when browsers are the client (REST).

WebSockets & Server-Sent Events

Push updates to clients. SSE is one-way and simpler (and how most AI chat responses stream); WebSockets are two-way.

Pick SSE for live feeds and streaming text; WebSockets for chat, games and collaboration.

Vitest & Jest

Unit test runners for JS/TS. Vitest is fast, Vite-native, Jest-compatible, and one of the fastest-growing tools in State of JS 2025.

Pick Vitest for new projects; keep Jest where it's already set up.

Playwright & Cypress

End-to-end tests that drive real browsers. Playwright's usage grew fastest in State of JS 2025.

Pick Playwright for new projects (all major browsers, fast, parallel). Keep a few E2E tests for critical flows; they're slow and can be flaky.

pytest, JUnit, xUnit

The standard test runners for Python, Java and .NET.

Pick them as the default in their ecosystems. Test behavior, not implementation details.

Game engines

Godot

Free, open-source engine with a lightweight editor and the Python-like GDScript (C# also supported). Adoption has been rising fast among indie developers and game jams.

Pick it when you make 2D or small/medium 3D games, start out, or want no licensing fees.

Pick something else when you target consoles directly or need cutting-edge 3D (Unity, Unreal).

Unity

Hugely popular C# engine with a big asset store, strong on mobile and cross-platform.

Pick it when you make mobile games, want the most tutorials and assets, or need console support.

Pick something else when you want a fully open-source engine (Godot) or AAA-level 3D graphics (Unreal).

Unreal Engine

The high-end 3D engine (C++ and Blueprints visual scripting), now the most common primary engine among professional studios.

Pick it when you aim for realistic 3D, console/PC releases, or a job at a large studio.

Pick something else when the game is 2D, for mobile or web, or a small first project.

GameMaker

Engine focused on 2D, with a quick learning curve.

Pick it when you make 2D games and want to see results fast.

Pick something else when you want 3D (Godot, Unity).

Phaser

2D game framework for the browser in JavaScript/TypeScript.

Pick it when the game should run in a browser with no install, or you already know JS.

Pick something else when you need 3D or console releases.

Three.js / Babylon.js

3D rendering in the browser with WebGL/WebGPU.

Pick it when you build web 3D: product viewers, visualizations, small browser games.

Pick something else when you need a full editor and engine toolset (Godot, Unity).

Bevy

Data-driven (ECS) game engine in Rust; code-first, no visual editor yet.

Pick it when you love Rust and want to learn engine architecture.

Pick something else when you want to ship a game soon with a mature editor (Godot).

Pygame / LÖVE

Simple 2D game libraries for Python and Lua.

Pick it when you learn programming through games.

Pick something else when you plan a commercial release (Godot, Unity).

MicroPython & Arduino (embedded)

Program microcontrollers in Python (MicroPython) or simplified C++ (Arduino).

Pick it when you build hobby electronics, IoT prototypes or learn hardware.

Pick something else when you need tight timing or minimal power use in a product (C, C++, Rust).

How to choose

  • What your team knows beats a small technical edge. A familiar tool shipped beats a perfect one half-learned.
  • Boring is good. Mature tools have answers online, stable APIs and fewer surprises. Try new things on side projects first.
  • Fit the shape of the problem: relational data → SQL; real-time → WebSockets/Elixir; CPU-heavy → compiled language; content site → static.
  • Count every moving part. Each extra service, queue or database needs monitoring, upgrades and backups.
  • Check health before adopting: recent releases, open issue activity, docs quality, and who maintains it.
  • Learn fundamentals over frameworks. HTTP, SQL, data structures, Git and the terminal transfer to every stack.

06Working with AI

AI assistants are great at drafting, explaining and reviewing. They're also confidently wrong sometimes. These rules keep you fast without shipping code nobody understands.

Ground rules

  1. You own every line. If you can't explain what a piece of code does and why, it isn't ready to commit, no matter who wrote it.
  2. Decide what "done" means before you ask. Write the goal, the constraints and how you'll check it (tests, example inputs and outputs).
  3. Give context, not just a command. Relevant files, error messages, language and framework versions, project conventions. With coding agents, keep a project instructions file (like CLAUDE.md) with build/test commands and rules.
  4. Work in small steps. One feature or fix per request, small diffs you can actually read. Big "build the whole app" requests produce code you can't review.
  5. Ask for a plan first on anything non-trivial, and correct the plan before any code is written. Fixing a plan is cheap; fixing 500 lines is not.
  6. Verify, don't trust. Run the code and the tests. Check unfamiliar APIs and packages against official docs: assistants can invent functions, options and even package names.
  7. Commit before big changes so you can diff and revert. Version control is your undo button.
  8. Never paste secrets (API keys, passwords, customer data) into prompts. Use placeholders.

Keeping quality high

  • Tests are the contract. Have tests written (or write them yourself) first, then ask for code that makes them pass. Never accept "fixing" a failing test by weakening it.
  • Read the diff like a reviewer. Look for: invented APIs, swallowed errors (catch {}), hard-coded values, missing input validation, SQL built with string concatenation, duplicated logic, and unrelated "while I'm here" edits.
  • Watch for scope creep. If you asked for a bug fix and got a refactor, ask for the minimal change instead.
  • Keep the architecture yours. AI follows patterns it sees. Point it at your existing modules so it extends them instead of inventing parallel ones.
  • Use static checks: types, linters, formatters and CI catch a whole class of AI mistakes automatically.
  • Security review anything touching auth, payments, file paths, user input or shell commands. Ask the AI to review for vulnerabilities too, then verify the findings yourself.
  • Check dependencies before installing: is the package real, maintained, and spelled right? Typosquatted packages are a known attack.
  • Refactor after it works. AI code is often verbose; simplifying it is also how you come to understand it.

Learning while using AI

If your goal is to get better (not just to finish a task), use AI as a tutor, not a vending machine.

  • Try first, for 15–20 minutes. Then ask for a hint, not the answer: "Don't give me code, what should I look at?"
  • Ask why. "Why is this O(n log n)?", "What breaks if I remove this line?", "What's the trade-off versus X?"
  • Explain it back. Describe your understanding and ask the AI to correct it.
  • Have it quiz you on a topic, or generate edge cases for your code that you then fix yourself.
  • Rewrite from memory. After seeing a solution, close it and rebuild it. Step through it in the bench to make sure you really get it.
  • Ask for review, not rewrites: "Review my code; point out bugs and style issues but don't fix them."

Red flags

  • "It works" but nobody ran it, or the tests were changed to pass.
  • A function, flag or package you can't find in the official docs.
  • Huge diffs for small requests, or files changed that had nothing to do with the task.
  • Errors silenced instead of handled; any types or disabled lint rules sprinkled in.
  • You keep pasting errors back and forth without understanding them. Stop, read the error, and debug one step yourself.
The short version: be specific about the goal, work in small reviewed steps, verify with tests and docs, and make sure you could have written (or at least explained) every line yourself.
