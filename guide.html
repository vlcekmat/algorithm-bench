01Algorithms

Each entry gives the idea in one line, its cost, when to reach for it, and the mistake people usually make. Costs use n for items, V and E for graph nodes and edges.

Sorting

In real code, call the language's built-in sort (usually Timsort or introsort). Knowing these matters for interviews, for custom orderings, and because their ideas (divide and conquer, partitioning, heaps) appear everywhere.

Bubble sort Try it

Swap neighbors that are out of order; each pass bubbles the largest item to the end.

Use it to learn. Stop early when a pass makes no swaps.

Insertion sort Try it

Grow a sorted prefix; slide each new item left until it fits.

Use it for tiny or nearly sorted arrays. Real sorts switch to it below ~16 items.

Selection sort Try it

Find the minimum of the unsorted part and swap it into place.

Use it when writes are expensive: at most n−1 swaps.

Merge sort Try it

Split in half, sort each half, merge the two sorted halves.

Use it when you need stability or guaranteed n log n, for linked lists, or for external sorting of huge files.

The merge step needs O(n) extra memory for arrays.

Quicksort Try it

Pick a pivot, partition smaller items left and larger right, recurse on both sides.

Use it as the fast in-memory default. Quickselect finds the k-th smallest in O(n) average.

Always picking the first or last element as pivot degrades to O(n²) on sorted input; pick randomly or median-of-three.

Heapsort

Build a max-heap, then repeatedly move the max to the end.

Use it for guaranteed O(n log n) with O(1) extra memory.

Counting / radix sort

Don't compare: count occurrences of each key, or sort digit by digit.

Use it for integers or short strings in a small range: beats n log n.

Searching

Binary search Try it

O(log n)O(1) space

On sorted data, compare with the middle and throw away the half that can't contain the answer.

Off-by-one errors: decide whether hi is inclusive and keep it consistent. Use lo + (hi - lo) / 2 in languages with overflow.

Binary search on the answer

O(log range · check)

If "can we do it with x?" is false then true as x grows, binary-search the smallest x that works.

Signals: "minimum maximum", "smallest capacity", "fewest days".

Two pointers Try it

O(n)

Move two indices toward each other (or in the same direction) and use sortedness to skip work.

Use it for pair sums in sorted arrays, removing duplicates in place, merging, palindromes.

Hash lookup

O(1) averageO(n) memory

Trade memory for time: store what you've seen so each lookup is instant.

Use it for "have I seen this?", counting, two-sum on unsorted data.

Graphs

Many problems are graphs in disguise: grids, dependencies, states of a puzzle, friendships, routes. First decide: directed or not, weighted or not, and whether there are negative weights or cycles.

Breadth-first search Try it

O(V + E)

Explore in rings using a queue; the first time you reach a node is via the fewest edges.

Use it for shortest paths in unweighted graphs and grids, levels, spreading processes.

Mark nodes as seen when you enqueue them, not when you dequeue, or you add duplicates.

Depth-first search Try it

O(V + E)

Go as deep as possible, then backtrack (recursion or an explicit stack).

Use it for connectivity, counting components, cycle detection, topological order, flood fill.

Deep recursion can overflow the stack on big inputs; switch to an explicit stack.

Dijkstra Try it

O((V + E) log V)

Always finalize the closest unfinished node, using a priority queue.

Use it for shortest paths with non-negative weights.

Wrong with negative edges. Skip stale queue entries whose distance is outdated.

A* search Try it

≤ Dijkstra in practice

Dijkstra ordered by g + h, where h estimates the remaining distance.

Use it for one start, one goal, with a good heuristic (maps, games).

h must never overestimate, or the path may not be shortest.

Bellman–Ford

O(V · E)

Relax every edge V−1 times; a further improvement means a negative cycle.

Use it with negative weights, or to detect negative cycles (arbitrage).

Floyd–Warshall

O(V³)O(V²) memory

For each middle node k, try improving every pair i→j through k.

Use it for all-pairs distances on small graphs (V ≤ ~400).

0-1 BFS

O(V + E)

Weights are only 0 or 1: push 0-edges to the front of a deque, 1-edges to the back.

Topological sort Try it

O(V + E)

Kahn: repeatedly output a node with no incoming edges. Or reverse DFS finish order.

Use it for build orders, course prerequisites, task scheduling.

If not every node comes out, the graph has a cycle.

Prim / Kruskal Try it

O(E log V)

Minimum spanning tree. Prim grows one tree with a heap; Kruskal adds the lightest edges that don't make a cycle, using union-find.

Use it to connect everything as cheaply as possible (networks, clustering).

Strongly connected components

O(V + E)

Tarjan (one DFS with low-links) or Kosaraju (DFS, reverse graph, DFS again).

Use it for groups that can all reach each other, 2-SAT, simplifying a graph to a DAG.

Bipartite check

O(V + E)

Two-color with BFS/DFS; a conflict means an odd cycle.

Use it for "split into two groups with no conflicts inside a group".

Trees & heaps

Traversals

Pre-order (node, left, right) copies/serializes. In-order (left, node, right) gives sorted order of a BST. Post-order (left, right, node) computes sizes/heights and deletes. Level order is BFS.

Binary search tree

O(h) per op

Left subtree < node < right subtree. Balanced variants (red-black, AVL) keep h = O(log n).

Inserting sorted data into an unbalanced BST makes a linked list: O(n) per op.

Heap / priority queue

O(log n) push/pop

A complete binary tree stored in an array; parent of i is ⌊(i−1)/2⌋. Building one from n items is O(n).

Use it for top-k, merge k sorted lists, running median (two heaps), schedulers.

Lowest common ancestor

O(log n) per query

Binary lifting: precompute 2k-th ancestors, then lift both nodes.

Trie

O(L)

A tree of characters; each path from the root spells a prefix.

Use it for autocomplete, word games, IP routing, many-pattern search.

Fenwick & segment trees

O(log n) query/update

Prefix sums (Fenwick) or any associative range query like min/max/sum (segment tree) that stays fast while values change.

Dynamic programming

DP = recursion + remembering answers to subproblems. Define the state (what you need to know), the transition (how a state is built from smaller ones), the base cases, and the order to fill. Start with memoized recursion; convert to a table if you need speed or less stack. Try the LCS table

Tell it's DP: the question asks for a count, a min/max, or yes/no over many choices, and a brute force recomputes the same sub-question again and again.

Greedy

Make the locally best choice and never look back. Fast and simple, but only correct when you can argue that a best choice now never blocks a better solution later (an "exchange argument"). If you can't argue it, try DP.

Interval scheduling

Sort by end time, keep every interval that starts after the last kept one ends. Maximizes the number of non-overlapping intervals.

Merging intervals

Sort by start, extend the current interval while the next one overlaps.

Huffman coding

Repeatedly merge the two least frequent symbols (heap). Optimal prefix codes.

Coin change, careful

Taking the largest coin works for 1/2/5/10 coins but fails for 1/3/4 (6 = 3+3, greedy gives 4+1+1). Classic greedy trap.

Strings

KMP

O(n + m)

Precompute, for each prefix of the pattern, its longest proper prefix that is also a suffix; never re-scan text characters.

Rabin–Karp

O(n + m) average

Rolling hash: compare hashes of windows, verify on match. Great for many patterns or duplicate substrings.

Z-function

O(n)

For each position, the length of the longest match with the string's prefix. Search by running it on pattern + '$' + text.

Palindromes

O(n²) / O(n)

Expand around each center (2n−1 centers) is simple and usually enough; Manacher does it in O(n).

Anagrams & counts

O(n)

Compare letter-count arrays; slide a window and update counts in O(1) per step.

Math & bits

GCD (Euclid)

O(log min(a, b))

gcd(a, b) = gcd(b, a % b), and lcm = a / gcd · b.

Sieve of Eratosthenes

O(n log log n)

Cross out multiples of each prime starting at p². All primes up to n.

Fast exponentiation

O(log e)

Square the base, multiply in when the current bit of the exponent is 1. Do it mod m for huge powers.

Modular arithmetic

Take % m after every + and ×. Division mod a prime p: multiply by a^(p-2) mod p (Fermat).

Bit tricks

x & (x-1) drops the lowest set bit; x & -x keeps it; XOR of all numbers cancels pairs; masks 0 … 2ⁿ-1 enumerate subsets.

Backtracking

Build a solution step by step; when a partial solution can't work, undo the last choice and try the next. It's DFS over the tree of choices. The art is pruning: stop exploring a branch as early as possible. Typical uses: permutations, subsets, combinations summing to a target, N-Queens, Sudoku, word search.

Sketch the choice tree in the Sketch tab with a binary tree and capture a step per decision: it makes the recursion click.

02Solving problems

Most problems are a known pattern in a costume. The process below gets you from "no idea" to working code without skipping the steps where bugs hide.

A process that works

  1. Restate the problem in your own words. Write down the input, the output, and the constraints (how big is n? can values be negative? duplicates? empty input?).
  2. Work two or three examples by hand, including an edge case: empty, one item, all equal, already sorted, negative numbers.
  3. Write the brute force first, even just in words, and state its cost. It's a correct baseline and often shows the waste.
  4. Find the bottleneck. What's repeated? Then look at the signals table below for a pattern that removes it.
  5. Check the budget. Use the n limit to pick the target complexity (n ≤ 10⁵ wants O(n log n) or better).
  6. Code it in small pieces with clear names. Get a simple version running before handling every edge case.
  7. Trace it. Step through your examples on paper or in the bench (the Your code tab shows every step()).
  8. Test the edges, then state the final time and space complexity.

Code templates

Skeletons in JavaScript. Paste one into the Your code tab, add step() calls, and watch it run.

Sliding window (longest valid window) Try it

function longest(s) {
  const count = new Map();
  let left = 0, best = 0;
  for (let right = 0; right < s.length; right++) {
    count.set(s[right], (count.get(s[right]) || 0) + 1);      // grow
    while (count.get(s[right]) > 1) {                         // invalid? shrink
      count.set(s[left], count.get(s[left]) - 1);
      left++;
    }
    best = Math.max(best, right - left + 1);
  }
  return best;   // longest substring without repeats
}

Prefix sums + hash map

// number of subarrays summing to k
function countK(nums, k) {
  const seen = new Map([[0, 1]]);
  let sum = 0, count = 0;
  for (const x of nums) {
    sum += x;
    count += seen.get(sum - k) || 0;
    seen.set(sum, (seen.get(sum) || 0) + 1);
  }
  return count;
}

Binary search on the answer

// smallest x in [lo, hi] where works(x)
// works must be false…false,true…true
function firstTrue(lo, hi, works) {
  while (lo < hi) {
    const mid = lo + Math.floor((hi - lo) / 2);
    if (works(mid)) hi = mid;
    else lo = mid + 1;
  }
  return lo;
}

Monotonic stack

// next greater element to the right
function nextGreater(a) {
  const res = Array(a.length).fill(-1);
  const stack = [];               // indices
  for (let i = 0; i < a.length; i++) {
    while (stack.length &&
           a[stack.at(-1)] < a[i])
      res[stack.pop()] = a[i];
    stack.push(i);
  }
  return res;
}

BFS on a grid Try it

function shortest(grid, sr, sc, er, ec) {
  const H = grid.length, W = grid[0].length;
  const dist = grid.map(r => r.map(() => -1));
  const q = [[sr, sc]]; dist[sr][sc] = 0;
  for (let h = 0; h < q.length; h++) {
    const [r, c] = q[h];
    if (r === er && c === ec) return dist[r][c];
    for (const [dr, dc] of [[1,0],[-1,0],[0,1],[0,-1]]) {
      const nr = r + dr, nc = c + dc;
      if (nr < 0 || nc < 0 || nr >= H || nc >= W) continue;
      if (grid[nr][nc] === '#' || dist[nr][nc] !== -1) continue;
      dist[nr][nc] = dist[r][c] + 1;     // mark when queued
      q.push([nr, nc]);
    }
  }
  return -1;
}

Union-find

const parent = [...Array(n).keys()];
const size = Array(n).fill(1);
function find(x) {
  while (parent[x] !== x) {
    parent[x] = parent[parent[x]]; // halve path
    x = parent[x];
  }
  return x;
}
function union(a, b) {
  a = find(a); b = find(b);
  if (a === b) return false;     // already linked
  if (size[a] < size[b]) [a, b] = [b, a];
  parent[b] = a; size[a] += size[b];
  return true;
}

Backtracking

function subsetsSumming(nums, target) {
  const out = [], pick = [];
  function go(i, sum) {
    if (sum === target) out.push([...pick]);
    if (sum >= target) return;         // prune
    for (let j = i; j < nums.length; j++) {
      pick.push(nums[j]);              // choose
      go(j + 1, sum + nums[j]);        // explore
      pick.pop();                      // undo
    }
  }
  go(0, 0);
  return out;
}

Memoized DP

// fewest coins to make amount (-1 if impossible)
function coins(cs, amount) {
  const memo = new Map();
  function f(a) {
    if (a === 0) return 0;
    if (a < 0) return Infinity;
    if (memo.has(a)) return memo.get(a);
    let best = Infinity;
    for (const c of cs) best = Math.min(best, f(a - c) + 1);
    memo.set(a, best);
    return best;
  }
  const r = f(amount);
  return r === Infinity ? -1 : r;
}

Fast & slow pointers

function hasCycle(head) {
  let slow = head, fast = head;
  while (fast && fast.next) {
    slow = slow.next;
    fast = fast.next.next;
    if (slow === fast) return true;
  }
  return false;
}

Designing real programs

Algorithms are a small part of most software. These habits matter more day to day:

  • Model the data first. Good types and names make the code obvious; most bugs live in unclear data.
  • Small functions with one job, and keep side effects (I/O, network, database) at the edges so the core is easy to test.
  • Make illegal states unrepresentable: enums instead of magic strings, required fields instead of "maybe null".
  • Validate at the boundary (user input, API responses, files) and trust your types inside.
  • Draw it. A class or sequence diagram (UML section of the Sketch tab) exposes coupling and missing steps before you write code.
  • Measure before optimizing. Pick the right algorithm up front; micro-optimize only what a profiler shows.

03Technologies

What the popular tools are for and when to pick them. Rules of thumb, not rankings: the best choice is usually what your team already knows well, as long as it fits the problem.

Languages

Python

Readable, huge ecosystem. Strong in data science, ML/AI, scripting, automation, backends (Django, FastAPI).

Slow for CPU-heavy loops (use NumPy or native extensions); dynamic types need discipline (type hints + mypy/pyright).

JavaScript / TypeScript

The language of the web; Node, Deno and Bun run it on servers. TypeScript adds static types and is the norm for serious projects.

Quirky equality and number semantics; npm dependency trees grow fast.

Java

Mature, fast JVM, strong typing. Strong in enterprise backends (Spring), Android legacy, big systems. Modern Java (records, pattern matching, virtual threads) is much less verbose.

Kotlin

Concise JVM language, null-safety built in. Default for Android; works anywhere Java does.

C#

.NET's language: backends (ASP.NET Core), desktop, games (Unity). Excellent tooling, similar niche to Java.

Go

Simple, fast to compile, great concurrency (goroutines). Strong in cloud services, CLIs, infrastructure (Docker and Kubernetes are written in Go).

Rust

C-level speed with memory safety checked at compile time. Strong in systems, performance-critical services, WebAssembly, CLIs.

Steep learning curve (ownership and lifetimes).

C / C++

Maximum control and speed: operating systems, embedded, game engines, competitive programming (C++ STL).

Manual memory management: buffer overflows and use-after-free bugs.

Swift

Apple platforms (iOS, macOS). Modern, safe, fast.

SQL

Not optional: almost every app stores data in a relational database. Learn joins, indexes, GROUP BY, transactions.

Frontend

HTML, CSS, JS first

Frameworks change; the platform stays. Semantic HTML, flexbox/grid and the DOM make every framework easier. Small sites (like this one) need no framework.

React

Component library with the largest ecosystem and job market. Pair with a framework (Next.js, Remix/React Router) for routing, data loading and server rendering.

Vue

Approachable component framework with single-file components; Nuxt is its full-stack framework.

Svelte

Compiles components into minimal JS; very little boilerplate. SvelteKit for full apps.

Angular

Batteries-included and opinionated (DI, forms, router, TypeScript). Common in large enterprise teams.

Tailwind CSS

Utility classes in markup; fast to build consistent UIs. Pairs well with component libraries.

Build tools

Vite is the common default dev server and bundler. npm, pnpm or yarn manage packages.

Mobile

Native (Swift, Kotlin) for the best platform fit; React Native or Flutter (Dart) for one codebase on both platforms.

Backend

Node.js (Express, Fastify, NestJS)

JavaScript on the server; great for I/O-heavy APIs and sharing types with a TypeScript frontend. NestJS adds structure for big apps.

Spring Boot

The Java standard: dependency injection, data access, security, huge ecosystem. Heavy but very capable.

Django / FastAPI / Flask

Python. Django: batteries included (ORM, admin, auth). FastAPI: modern typed APIs with automatic docs. Flask: minimal.

ASP.NET Core

C# web framework: fast, well documented, strong on Azure.

Ruby on Rails, Laravel

Convention-over-configuration frameworks (Ruby, PHP) that make CRUD apps very fast to build.

Go net/http, Gin, Echo

Small, fast services with few dependencies; easy to deploy as a single binary.

Databases & messaging

PostgreSQL

The safe default relational database: correct, feature-rich (JSON, full-text search, extensions).

MySQL / MariaDB

Widely hosted relational databases; simpler feature set, very common in web hosting.

SQLite

A database in a single file, no server. Perfect for apps, tests, prototypes and small sites.

MongoDB

Document store (JSON-like). Flexible schema; good when data really is document-shaped.

"No schema" still needs a schema in your code; relations and joins are weaker.

Redis / Valkey

In-memory key-value store: caching, sessions, rate limits, queues, leaderboards.

Elasticsearch / OpenSearch

Full-text search and log analytics.

Kafka

Durable, replayable event log for high-throughput streams between services.

RabbitMQ

Message broker for job queues and routing between services.

ORMs

Prisma, Drizzle, TypeORM (JS), Hibernate/JPA (Java), SQLAlchemy (Python), Entity Framework (C#). Fast to start, but learn the SQL they generate.

Tooling, infra & cloud

Git & GitHub/GitLab

Version control is non-negotiable: small commits, clear messages, branches and pull requests for review.

Docker

Package an app with its environment so it runs the same everywhere. Docker Compose runs several services locally.

Kubernetes

Runs and scales containers across many machines. Powerful, complex; most small projects don't need it.

CI/CD

GitHub Actions, GitLab CI and similar run tests and deploys on every push. Automate checks you'd forget.

Terraform / OpenTofu

Infrastructure as code: describe servers, databases and networks in files you can review and version.

Cloud providers

AWS (largest), Azure (strong with Microsoft shops), Google Cloud (data/ML). Learn the basics: compute, storage, managed databases, IAM.

Hosting platforms

Vercel, Netlify, Cloudflare, GitHub Pages, Render, Fly.io: deploy with a push, little ops work. Great for side projects.

Observability

Logs, metrics and traces (OpenTelemetry, Prometheus, Grafana, Sentry) tell you what's happening in production.

APIs & testing

REST

Resources over HTTP with standard verbs and status codes. Simple, cacheable, the default for public APIs. Describe it with OpenAPI.

GraphQL

Clients ask for exactly the fields they need from one endpoint. Good for complex frontends; harder caching and authorization.

gRPC

Typed, fast binary RPC between services (Protocol Buffers).

WebSockets / SSE

Real-time updates: chat, live dashboards, multiplayer.

Unit & integration tests

Vitest/Jest (JS), JUnit (Java), pytest (Python), xUnit (C#). Test behavior, not implementation details.

End-to-end tests

Playwright or Cypress drive a real browser. Keep a few for critical flows; they're slow and can be flaky.

Linters & formatters

ESLint, Prettier, Ruff, Checkstyle, rustfmt. Let tools settle style so reviews focus on logic.

How to choose

  • Boring is good. Mature tools have answers on the internet, stable APIs, and fewer surprises.
  • Fit the problem's shape: relational data → SQL database; real-time → WebSockets; CPU-heavy → compiled language.
  • Count the cost of each extra moving part. Every new service, queue or database needs monitoring, upgrades and backups.
  • Learn fundamentals over frameworks. HTTP, SQL, data structures, Git and the terminal transfer to every stack.

04Working with AI

AI assistants are great at drafting, explaining and reviewing. They're also confidently wrong sometimes. These rules keep you fast without shipping code nobody understands.

Ground rules

  1. You own every line. If you can't explain what a piece of code does and why, it isn't ready to commit, no matter who wrote it.
  2. Decide what "done" means before you ask. Write the goal, the constraints and how you'll check it (tests, example inputs and outputs).
  3. Give context, not just a command. Relevant files, error messages, language and framework versions, project conventions. With coding agents, keep a project instructions file (like CLAUDE.md) with build/test commands and rules.
  4. Work in small steps. One feature or fix per request, small diffs you can actually read. Big "build the whole app" requests produce code you can't review.
  5. Ask for a plan first on anything non-trivial, and correct the plan before any code is written. Fixing a plan is cheap; fixing 500 lines is not.
  6. Verify, don't trust. Run the code and the tests. Check unfamiliar APIs and packages against official docs: assistants can invent functions, options and even package names.
  7. Commit before big changes so you can diff and revert. Version control is your undo button.
  8. Never paste secrets (API keys, passwords, customer data) into prompts. Use placeholders.

Keeping quality high

  • Tests are the contract. Have tests written (or write them yourself) first, then ask for code that makes them pass. Never accept "fixing" a failing test by weakening it.
  • Read the diff like a reviewer. Look for: invented APIs, swallowed errors (catch {}), hard-coded values, missing input validation, SQL built with string concatenation, duplicated logic, and unrelated "while I'm here" edits.
  • Watch for scope creep. If you asked for a bug fix and got a refactor, ask for the minimal change instead.
  • Keep the architecture yours. AI follows patterns it sees. Point it at your existing modules so it extends them instead of inventing parallel ones.
  • Use static checks: types, linters, formatters and CI catch a whole class of AI mistakes automatically.
  • Security review anything touching auth, payments, file paths, user input or shell commands. Ask the AI to review for vulnerabilities too, then verify the findings yourself.
  • Check dependencies before installing: is the package real, maintained, and spelled right? Typosquatted packages are a known attack.
  • Refactor after it works. AI code is often verbose; simplifying it is also how you come to understand it.

Learning while using AI

If your goal is to get better (not just to finish a task), use AI as a tutor, not a vending machine.

  • Try first, for 15–20 minutes. Then ask for a hint, not the answer: "Don't give me code, what should I look at?"
  • Ask why. "Why is this O(n log n)?", "What breaks if I remove this line?", "What's the trade-off versus X?"
  • Explain it back. Describe your understanding and ask the AI to correct it.
  • Have it quiz you on a topic, or generate edge cases for your code that you then fix yourself.
  • Rewrite from memory. After seeing a solution, close it and rebuild it. Step through it in the bench to make sure you really get it.
  • Ask for review, not rewrites: "Review my code; point out bugs and style issues but don't fix them."

Red flags

  • "It works" but nobody ran it, or the tests were changed to pass.
  • A function, flag or package you can't find in the official docs.
  • Huge diffs for small requests, or files changed that had nothing to do with the task.
  • Errors silenced instead of handled; any types or disabled lint rules sprinkled in.
  • You keep pasting errors back and forth without understanding them. Stop, read the error, and debug one step yourself.
The short version: be specific about the goal, work in small reviewed steps, verify with tests and docs, and make sure you could have written (or at least explained) every line yourself.
